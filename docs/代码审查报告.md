## 详细说明

### 1. [P0] 电池/设备管理 Feature 常量错位

`GaiaConstants.kt:42-44`：

```kotlin
const val FEATURE_BATTERY: Int = 0x2C        // 注释：电池通知
const val FEATURE_DEVICE_MGMT: Int = 0x1A    // 注释：设备管理 (EQ预设选择等)
```

README:41-47 与 `webtest.py:20-36` 的权威映射是：`0x1A` = 电池，`0x2C` = 手势 TOUCHV2，`0x28` = 一拖二/设备信息。两份常量把 0x1A 与 0x2C 的语义**互换并整体错位**（`FEATURE_DEVICE_MGMT` 沿用了早期逆向文档对 0x1A 的旧称“设备管理”，其“EQ 预设选择”描述没有出处）。

补充：`FEATURE_BATTERY` / `FEATURE_DEVICE_MGMT` 在本仓库内没有调用点，所以“覆盖用户手势配置”是潜在风险而非现网行为；不过一旦按名称使用就会发错域，仍应修复。另外 `FEATURE_DEVICE_INFO = 0x28` 已经存在，不需要新增 0x28 常量。

连带后果：`GaiaConstants.kt:98-100` 的 `CMD_BATTERY_QUERY_1/2` 和 `CMD_BATTERY_NOTIFY = 0x03` 挂在 `0x2C` 名下。而 0x2C 的 `0x03` 是**手势整包写入**命令。任何按“读电量”意图调用 `(FEATURE_BATTERY, CMD_BATTERY_NOTIFY)` 的代码，实际会向手势域发写入命令，覆盖用户手势配置。

建议：改为 `FEATURE_BATTERY = 0x1A`、删除或重定义为 `FEATURE_TOUCH = 0x2C`，并把电池相关 Cmd 归到 `0x1A`（`0x00` 查询支持的电池、`0x01` 查询指定电池）。

### 2. [P0] 0x20 域把 LHDC 当成 LDAC

`GaiaConstants.kt:79-81`：

```kotlin
const val CMD_LDAC_STATUS: Int = 0x05
const val CMD_CODEC_SET: Int = 0x06
```

但 README:131-140 与 `webtest.py:165-170` 的映射是：`0x01` LC3 读、`0x02` LDAC 读、`0x03` LC3 写、`0x04` LDAC 写、`0x05` **LHDC 读**、`0x06` **LHDC 写**。`docs/MOONDROP_Pudding_逆向结果.md:5` 的修订注也写明「0x20 cmd 0x05 为 LHDC」。

实测（Python 侧同帧解析）：`FF 04 00 01 00 1D 21 05 01` 被 `webtest.decode_packet` 标注为「LHDC: 开」。而 `GaiaPacketBuilder.ldacStatusQuery()`（`GaiaPacketBuilder.kt:46`）和 `ResponseParser.parseLdacStatus()`（`ResponseParser.kt:63-68`）都把它当 LDAC。

后果：用库查询“LDAC 状态”，实际读到的是 LHDC 开关状态；`parseLdacStatus` 还会给出确定的 true/false，调用方无从察觉。

建议：新增 `CMD_LHDC_STATUS = 0x05` / `CMD_LHDC_SET = 0x06`，把 LDAC 读改回 `0x02`，并补 `0x03/0x04` 写入常量。

### 3. [P0] ANC/Gain 解析不校验命令号与错误位

`ResponseParser.kt:40-44`：

```kotlin
fun parseAncMode(packet: GaiaPacket): AncMode? {
    if (GaiaConstants.baseFeatureId(packet.featureId) != GaiaConstants.FEATURE_ANC) return null
    if (packet.payload.isEmpty()) return null
    return AncMode.fromValue(packet.payload[0])
}
```

只校验 Feature 的基值，不校验 `commandId`，也不校验帧是否为错误帧。真实的 ANC 错误帧形如 `FF 04 00 01 00 1D 41 84 06`（feature=0x41、cmd=0x84 带错误位、payload=[0x06]），本函数会取 `payload[0]=0x06`，经 `Enums.kt:18` 的 `map[value] ?: OFF` 静默回落为 `AncMode.OFF`——把一次失败当成“已关闭降噪”。

`parseGainLevel`（`ResponseParser.kt:56-60`）同理，未知值回落为 `MEDIUM`（`Enums.kt:32`）。

建议：增加 `commandId` 白名单（query/set 且非 `|0x80` 的响应），并对 `fromValue` 的未知值返回 null 而不是静默兜底。`AncMode.fromValue` 与 `GainLevel.fromValue` 的静默兜底本身也应改成可空。

### 4. [P0] `isError` / `isSuccess` 判定依据与协议不符

`ResponseParser.kt:78-84`：

```kotlin
fun isError(packet: GaiaPacket): Boolean =
    packet.payload.isNotEmpty() && packet.payload[0] == 0xFE.toByte()

fun isSuccess(packet: GaiaPacket): Boolean =
    packet.payload.isEmpty() || packet.payload[0] == 0x00.toByte()
```

README:27-33 与 `webtest.py:232-236` 的帧类型规则是：错误帧 = `cmd | 0x80` **且** `feature | 0x01`，payload 放错误码（0..7，见 `webtest.py:46-49`）。`0xFE` 既不在错误码表，也未出现在任何抓包记录中（`docs/...:140-144` 只列出 `0x06`）。

实测：`FF 04 00 01 00 1D 41 84 06` 被 `webtest` 正确识别为 `error`，而按 Kotlin 逻辑 `isError=false`、`isSuccess=false`，调用方拿到两个 false 无法判断。反过来，`41 04 00`（成功回显 0）的 `isSuccess=true` 只是巧合。

建议：错误判定改为 `isResponse(featureId) && (commandId and 0x80) != 0`；成功判定改为“有响应且非错误”。SET 响应会回显写入值（例如 `41 04 01`），不能再把 `payload[0]` 是否为 0 当成成功条件。

### 5. [P1] `GaiaCodec.decode` 忽略 Len，与 `StreamDecoder` 不一致

`GaiaCodec.kt:43-55` 解码时完全跳过 `data[2..3]`：

```kotlin
val payload = if (data.size > 8) data.copyOfRange(8, data.size) else byteArrayOf()
```

而 `StreamDecoder.drain()`（`GaiaCodec.kt:95-99`）是严格按 Len 切帧的。两者对同一段字节会给出不同结果：

- 声明 Len=5、实际只给 1 字节：`decode` 接受并返回 `payload=[0x33]`；`StreamDecoder` 会继续等待。
- 声明 Len=0、实际多给 2 字节：`decode` 返回 `payload=[0xAA,0xBB]`；Python 侧实测返回 `payload=[]`（多余字节被丢弃）。

实测（Python 侧，行为与 Kotlin `decode` 相反，可作对照）：声明 5 实际 1 → `None`；声明 0 实际 2 → `[]`。

建议：`decode` 增加 `len = (data[2] shl 8) or data[3]`，要求 `data.size == 8 + len`（或允许尾随字节时明确截断），并与 `StreamDecoder` 共用同一套校验。

### 6. [P1] `StreamDecoder` 对 Len 无上界校验

`GaiaCodec.kt:95-99`：

```kotlin
val len = ((buffer[head + 2].toInt() and 0xFF) shl 8) or (buffer[head + 3].toInt() and 0xFF)
val totalLen = 8 + len
if (tail - head < totalLen) break
```

`len` 最大可声明 `0xFFFF`，`totalLen` 可达 65543。一旦收到 Len 字段被污染（或长度字段其实是别的语义）的帧，解码器会一直 `break` 等待，后续正常帧全部滞留，`feed` 还会随收到的数据继续扩容缓冲区。实测 Python 侧对 `Len=0xFFFF` 直接返回 `None`，Kotlin 侧无对应防护。

建议：增加 `MAX_PAYLOAD`（如 512 或抓包观察到的最大值）上限；超限时按“错帧”丢弃并前移 1 字节重新同步，而不是 `break`。

### 7. [P1] `_payload_of` 把异步通知当作查询响应

`webtest.py:626-630`：

```python
def _payload_of(result):
    d = result.get("decoded") if result else None
    if not d or d.get("frame_type") == "error":
        return None
    return d.get("payload")
```

只排除了 `error`，没有排除 `notification`。实测：`FF 04 00 01 00 1D 40 81 04`（ANC 异步推送）的 `frame_type=notification`，`_payload_of` 返回 `[4]`。`read_state()`（`webtest.py:760-762`）用 `payload("anc")` 取 `state["anc"]`，于是推送值会被当成查询结果。

建议：`_payload_of` 增加 `frame_type == "notification"` 时返回 `None`；或在 `send_cmd` 里按期望的响应特征（feature 带响应位且 cmd 与请求一致）过滤帧。

补充：`send_cmd` 在写前会 `reset_input_buffer()`，只有查询窗口内到达的通知才会被误读；DEMO 的 MockSerial 会直接丢弃 `cmd & 0x80` 的帧，所以第 7 条不能通过 `/api/send` 回放，只能直接调用 `decode_packet` / `_payload_of` 验证。

### 8. [P1] 写操作走 GET 且无 Origin 校验，本地 CSRF

`webtest.py:2085-2121` 所有写接口（`/api/set/anc`、`/api/set/touch`、`/api/set/tone` 等）都是 GET，且 `Handler` 不校验 `Origin` / `Referer` / `Host`（`webtest.py:2041-2143`）。服务绑定 `127.0.0.1`（`webtest.py:2228`），远程无法直连，但任意网页可以用 `<img src="http://127.0.0.1:8080/api/set/touch?hex=0000000000">` 这类简单请求触发写操作——浏览器不会因此发起预检。这会静默清空用户手势或切换降噪。

建议：写接口改为 POST + JSON，或在服务端校验 `Sec-Fetch-Site` / `Origin` / `Referer` 只允许同源；至少拒绝带外部 `Origin` 的请求。本次采用了后者（同源校验），API 仍为 GET。

systemProp.http.proxyPort=7890

### 12. [P2] `feature_id` 是凭空的移位解释

官方 APK 复核确认 `webtest.py:19` 的注释是对的：帧里的 Feature 字节 = `feature_id << 1`，APK 的 `QTILFeature` 也是 BASIC(0)、BATTERY(13)、ANC_V2(32) 等 7 位 ID。`webtest.py:241` 的 `"feature_id": base_feature >> 1` 因此不是凭空移位——实测 `0x40` 帧的 `feature_id` 为 32，正是 ANC V2。该字段未被 UI 使用；混淆来自 README 表格用原始字节命名（0x40），两种命名并存即可。

说明：此前把「0x40 帧显示成一拖二」归咎于这里，是误判。实测 `feature_name(0x40)` 返回 `ANC V2` 是正确的；那次现象的真实原因是第 13 条（API 把 `feature=40` 当十进制 0x28）。

### 13. [P2] `_req_int` 的进制解析会静默改值

`webtest.py:2022-2032` 使用 `int(str(raw), 0)`。UI 侧 JS 已把 hex 转成十进制再发（`webtest.py:1893-1910`），所以面板没问题；但直接调 API 时：

- `feature=40` → `int("40", 0)=40=0x28`（实测发出 `FF 04 00 00 00 1D 28 03`）
- `feature=0x40` → 64 → 正确
- `feature=08` → `ValueError` → 400

更正：README 并没有 `F:0x40` 的自定义命令示例，`F:0x` 只出现在网页日志和预设按钮的 title（`webtest.py:1441`、`:2000`）；README 的 API 表只有 `GET /api/send?feature=&cmd=&payload=`。

建议：若要统一按十六进制解析，必须同时修改 `sendCustom()`（它现在把输入框的十六进制转成十进制再发，直接改 `int(raw, 16)` 会把 UI 传来的十进制 `64` 解析成 `0x64`），以及 `/api/presets` 的调用方。在此之前，建议在 README 和页面上明确：`feature`/`cmd` 是 Python 整数字面量，`40` = 十进制 40（0x28），`0x40` = 0x40。

### 14. [P2] MockSerial 丢弃尾部半帧

`webtest.py:311-328` 的 `write()` 逐帧切分，遇到 `len(rest) < total` 直接 `break`，不缓存剩余字节。真机路径下 `send_cmd` 每次只写完整帧，暂不触发；但自定义命令与多帧写入混合时是潜在丢帧点。建议增加 `self._pending` 缓冲，与 `_recv_frame` 的粘包处理保持一致。

### 15. [P2] `set_tone` 读不到当前值时静默用默认值写入

`webtest.py:936-950`：

```python
base = before or [1, 60, 1]
```

读前置状态失败时，未指定的字段会按 `[1, 60, 1]` 补齐并整包写入。这意味着“只改音量”的请求可能在设备原组号未知的情况下把组号写成 1。`set_touch`（`webtest.py:929-931`）对同类情况会给出 `warning`，`set_tone` 则没有。建议：读失败时若请求字段不全，直接 `ValueError` 拒绝，或至少回传 warning。

### 16. [P2] `Testing.bat` 启动顺序与依赖检查

### 17. [P2] `fix_rfc.ps1` 的健壮性

`tools/fix_rfc.ps1:2,6,9`：

- `Get-PnpDevice | Where-Object { $_.InstanceId -match 'MS_RFCOMM' }` 可能匹配多个设备；`Disable-PnpDevice -InstanceId` 的参数类型是 `String[]`，传数组不会报错，而是把所有匹配设备一起禁用。原脚本还会在 `$rfcomm.Status` 等插值处输出数组内容。
- 缺少 `#Requires -RunAsAdministrator`，非管理员下 `Disable/Enable-PnpDevice` 必然失败，但被 `-ErrorAction SilentlyContinue` 吞掉，脚本仍打印「结果: ...」，容易误判为成功。
- 建议：取第一个设备、显式检查管理员权限、失败时输出错误而不是静默。

### 18. [P2] 文档之间的四处矛盾

1. **Len 语义**：`docs/...:26` 写 `Len = 1(Feature) + 1(Cmd) + Payload.size`，`docs/...:34` 与 `README.md:22`、`GaiaCodecTest.kt:44-48` 都写 `Len = payload.size`；`GaiaCodec.kt:24-26` 的行内注释也是 payload size，但同一文件的类注释（13-14 行）、`GaiaConstants.kt:10-11` 和 `GaiaPacket.kt:10` 仍写着 `Len = 1 + 1 + payload.size`，代码注释本身也自相矛盾。报告原先引用的“抓包样本 `FF 04 00 01 00 1D 40 04 02`”在仓库中查不到，属自拟示例；仓库里能查到的样本大多是 Len = payload 长度，但 `docs/...:176-178` 的 LHDC SET 回包记录为 9 字节、Len=2 而 payload 只有 1 字节，疑似记录截断，需回看原始 btsnoop 复核。
2. **0x05 功能**：`docs/...:5` 的修订注说「0x20 cmd 0x05 为 LHDC」，但 `docs/...:170-171` 仍写「0x05 LDAC 状态查询」，同一文档内自相矛盾。
3. **Trailing Byte**：`docs/...:20,32,38` 说 TX 帧末尾有额外字节（`0x9A`/`0x29`），但 `docs/...:34` 的总长公式和两份实现的 `build_tx` / `GaiaCodec.encode` 都没有该字节。若该字节真实存在，两实现与真机抓包不符；若不存在，文档该段应删除。
4. **Seq 递增**：`docs/...:27` 说「序列号，每包递增」，但所有抓包样本 offset 4 均为 `0x00`，两份实现也都固定发 `0x00`。补充：README 又说 Vendor 是 16 位 `0x001D`，而样本第 4-5 字节恰为 `00 1D`，因此第 4 字节更可能是 Vendor 的高字节；Kotlin 却把它当作 `sequence`（`GaiaCodec.kt:27`）且只校验第 5 字节（`:47`）。若按 16 位 Vendor 处理，`sequence` 字段应删除或改为固定 0。

### 19. [P2] README 增益方向描述含混

`README.md:265` 写「UI 标签与协议值方向相反：低 = `0x02`」。`Enums.kt:25-28` 与 UI（`webtest.py:1234-1236`）都是 高=0x00 / 中=0x01 / 低=0x02，映射本身一致；若把“方向”理解为标签次序（高→低）与数值次序（00→02）相反，这句话也能自圆其说，但容易被读成“需要取反映射”。建议直接写数值对应关系，不要用“方向相反”这种含混描述。

### 20. [P3] 测试覆盖缺口

`GaiaCodecTest.kt` 覆盖了编解码常规路径、被拆分的流式帧、逐字节喂入，但缺少以下用例——上面 P0/P1 的多数问题只要有一条对应用例就会立即暴露：

- 错误帧解析（`cmd | 0x80` + feature 响应位），验证 `isError` / `isSuccess`
- `Len` 与 payload 实际长度不一致的输入

## 补充复核（2026-11-07 APK 控制 ID）

对官方 APK v2.25.0c 复核后发现，原报告未覆盖 `0x00` 基础域的命令语义错位（详见 `_inspect/apk_control_id_audit.md`）：

- `0x01` 支持特性（首字节 more，后接 `[featureId][version]` 成对列表，不是 Feature 位图），不是“支持的命令列表”
- `0x03` 设备序列号；`0x05` 应用/固件版本
- `0x07` 注册通知、`0x08` 取消通知，不是“EQ 状态”
- `0x0C` 读取传输信息（Payload=ProtocolInfo id 1..7）、`0x0D` 设置传输参数（写），不是“配置查询/设备状态”
- `0x14/0x15` 左/右耳序列号，不是“序列号/设备 ID”
- `0x40 0x29` 是 ANC 切换配置读取，不是“可用模式查询”
